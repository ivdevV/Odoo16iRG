BLOQUEANTE
================================================================================

1. write() authorization is a client-controlled context key
   File: addons-extra/extrairg/irg_business_api/models/api_operation.py
   (write at ~92-95, _irg_internal_write at ~346-347)
   Related: models/elearning_service.py apply_create_slide / apply_create_section

   write() allows any vals, including state/snapshots, when
   context['irg_api_internal'] is set. In Odoo 16 that key is not a server
   secret: JSON-RPC/XML-RPC execute_kw and /web/dataset/call_kw take context
   from the client. The API group has perm_write=1, so the robot user can:

     write([id], {'state': 'applied'}, context={'irg_api_internal': True})

   That forges applied/verified without action_approve / irg_approve_operation.
   The same call can rewrite proposed_after; apply_create_slide() then does
   slide.slide.create(dict(proposed)) with whatever extra keys were planted
   (partner_ids, datas, user_id, …), which breaks “no memberships / attachments
   / authors” and the advisor rule that write() must not forge state.

   test_write_cannot_forge_applied_state only calls write() without that
   context, so it misses the bypass.

   Fix:
   - write() must always raise AccessError (no context gate).
   - _irg_internal_write() must call super(IrgApiOperation, self).write(vals)
     so it never re-enters the override.
   - Apply paths must create/write from an explicit allowlist of fields, not
     the raw proposed mapping.
   - Add a test: with_user(api_user).with_context(irg_api_internal=True)
     .write({'state': 'applied'}) still raises, and proposed_after cannot be
     swapped before approve.

MENOR
================================================================================

2. No row lock on apply — race can duplicate drafts
   File: models/api_operation.py (_irg_apply_preview)
   Two concurrent action_approve / irg_approve_operation on the same preview
   can both pass the state check and create two slides. Lock the operation
   row (FOR UPDATE / self.lock()) before applying. Also map IntegrityError on
   the unique idempotency constraint to the existing-record replay path.

3. Apply create trusts the full proposed dict
   File: models/elearning_service.py (apply_create_slide, apply_create_section)
   Even after fixing write(), keep an allowlist at apply time so a snapshot
   cannot grow extra ORM fields.

4. _irg_apply_preview does not call _irg_check_actor
   File: models/api_operation.py
   Callers do. Re-check group+owner inside apply so sudo cannot run if a new
   entry point appears.

5. paginate() materializes the full recordset then slices
   File: models/api_serializer.py
   Fine for this delivery size; search(limit/offset) would scale better.

6. Non-UserError on bad ints
   File: models/api_serializer.py paginate; models/elearning_service.py sequence
   int('x') raises ValueError (500) instead of UserError.

7. Update-draft preview of a published slide is allowed
   File: models/elearning_service.py preview_update_slide
   Apply later rejects. Reject at preview so the command never looks approvable.

8. Test gaps
   No test that unlink is denied, that academic models have no ACL for the
   API group, or that sudo is refused without the group on the apply site.
   Survey read has no happy-path assertion (only missing id).

9. changed_fields uses `set(proposed) - set(before) or [diffs]` so it reports

10. Form view leaves operation_code / payload / environment editable while

11. State awaiting_approval is never assigned.

12. SECRET_TOKENS uses substring match ('datas' in 'metadata').

Verdict
================================================================================
Phases 0–2 are otherwise implemented to the plan. One security hole remains
on the command model’s write() gate, which is in the threat model (Lisa
update_record / ORM write) and is trivial to exploit via RPC context.

BLOCK: write() trusts client context irg_api_internal, so the API user can forge state and proposed_after without the official apply path.
